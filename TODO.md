# AI Engineering Assist TODO

These items improve developer and technical-lead assistance. They do not expand the framework into PR governance, approvals, CI/CD, deployment, or release management.

| Priority | Capability | Intended outcome |
| --- | --- | --- |
| Next | Worked examples | Show proportionate low/moderate and high-risk assistance without requiring every artifact. |
| Next | Pilot project profile | Prove that a developer can find local commands, relevant guidance, and existing project-process links quickly. |
| Next | Unified change record | Allow requirements, plan, validation, readiness findings, and handoff to live in one concise record where appropriate. |
| Later | Local artifact validation | Check objective structure, references, and missing fields without pretending to approve engineering judgement. |
| Later | Measurement | Measure useful findings, developer time, false alarms, documentation freshness, and handoff quality. |

## Explicitly out of scope

- Defining or enforcing pull-request and reviewer policy.
- Recording or granting organizational approvals and exceptions.
- Creating or replacing CI/CD checks, branch protections, release gates, or deployment processes.
- Making merge, release, production, incident, or rollback decisions.

Projects own those processes and may link them from the project profile.

## Future extension rule

Additional capabilities may be proposed as needs emerge. They remain optional project extensions until an explicit shared design decision and pilot evidence justify adding them to the common baseline.
